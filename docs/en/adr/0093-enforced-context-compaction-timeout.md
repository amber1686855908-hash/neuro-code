# ADR 0093: Enforced context-compaction wall-clock timeout

- Status: accepted
- Date: 2026-08-08
- Scope: application memory boundary for future Runtime integration

## Context

Stage5DL defined when an explicit compaction request is safe, but its budget
did not yet enforce a wall-clock limit. A provider or persistence adapter that
waits indefinitely must not be allowed to turn a future compaction call into an
unbounded Runtime operation.

## Decision

Extend `neuro_code.application.memory.compaction_runtime` with:

- a finite `max_wall_time_seconds` in `ContextCompactionRuntimeBudget`;
- a default of 30 seconds and a hard upper bound of 300 seconds;
- `ContextCompactionTimeoutError` for an operation cancelled by that limit;
- an `asyncio.timeout` boundary around the existing explicit trigger only
  after the request has passed the safe-boundary gate.

The gate catches only the timeout generated by its own deadline and converts
it to the typed compaction timeout error. Provider errors, storage errors, and
`asyncio.CancelledError` continue to propagate unchanged. Disabled,
non-actionable, unsafe, and already-cancelled requests remain side-effect-free
no-ops and do not start a timeout context.

The timeout covers both summary generation and the subsequent persistence call.
It does not claim a transaction spanning Provider generation and storage. If a
storage adapter is cancelled at the deadline, the gate returns no success
result; adapter-level rollback remains the storage contract's responsibility.

## Consequences

Context compaction now has an enforced finite operation boundary without
changing `AgentRuntime`, Provider interfaces, events, ordinary turn budgets,
or automatic compaction. A future Runtime integration must still decide how to
report a timeout and must not treat a timeout as a persisted successful
compaction.
