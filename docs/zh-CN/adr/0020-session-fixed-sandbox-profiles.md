# ADR 0020：会话固定的沙箱 profile

**简体中文** · [English](../../en/adr/0020-session-fixed-sandbox-profiles.md)

## 背景

操作系统沙箱会在供应商和工具组合前选定；Linux 进程通过 bubblewrap 重新执行后，该边界
不可逆。待恢复会话的创建 profile 可能不同于今天的默认值、用户配置或项目配置。如果
静默应用当前值，就会改变已有对话的安全与能力边界。

固定的历史 Rust 基线会保存创建 profile，并在恢复时还原。显式 CLI/环境变量请求经过
规范化后若与保存值不同，就会被拒绝；在该元数据出现以前创建的会话仍沿用配置行为。

## 决策

SQLite schema v3 新增可空的 `sessions.sandbox_profile`：

- 每个新建的原生会话都保存一个规范内建 `SandboxProfile`，包括 `off`；
- 支持的上游导入会保留能够识别的内建 profile；
- 迁移会话或缺少元数据的导入会话保留 `NULL`，并按旧会话处理；
- 不支持或损坏的保存值失败关闭，不能伪装成旧会话。

按明确 ID 恢复时采用以下启动顺序：

1. 解析普通配置和状态数据库路径；
2. 通过 immutable 只读 SQLite 连接只检查所选会话的 profile；该连接不能创建数据库、
   WAL/SHM 文件或执行迁移；
3. 用保存值解析本次请求；
4. 强制执行或校验最终进程沙箱；
5. 初始化/迁移 SQLite，再组合供应商、权限和工具。

解析规则是确定性的：

| 保存的 profile | 显式 CLI/`NEURO_CODE_SANDBOX` | 结果 |
|---|---|---|
| 缺失 | 任意或缺失 | 使用普通配置解析 |
| 存在 | 缺失 | 还原保存的 profile |
| 存在 | 规范化后相同 | 还原保存的 profile |
| 存在 | 不同 | 在沙箱/供应商组合前失败 |

用户/项目配置不属于显式恢复覆盖，保存值优先。`readonly` 等别名会先解析再比较。因此用户
可以显式确认相同值，但不能在恢复期间加强或弱化某个会话。

`AgentConversation.open` 还会把已加载摘要与活动运行时 profile 再次比较，作为纵深防御。
已经运行的 TUI 无法更换进程沙箱，所以会话选择器会禁用 profile 不同的会话，并提示用
`--resume SESSION_ID` 重启。`NULL` 旧会话仍可在活动 profile 下选择。

## 影响

schema v1 会经过 v2 迁移到 v3，v2 也会直接迁移到 v3，均不改写已有会话数据。JSON 会话
导出版本升级为 3；会话列表/导出摘要会公开规范 profile 或表示旧会话的 null。

启动预读会拒绝活动 SQLite WAL，避免忽略尚未 checkpoint 的元数据。检查之后才参与竞争
的写入者仍会被后续普通加载与 `AgentConversation` 不匹配校验拦截，且发生在模型轮次或
工具动作之前。Neuro Code 当前不协调对同一状态目录的多个并发写入者。

当前 Python 适配器无法实施 `devbox` 等自定义上游 profile，因此导入时会拒绝，而不是
降级。最近会话恢复、会话分叉、自定义 profile 定义以及已有会话的 profile 迁移仍是独立
的未来能力。

源证据来自历史提交 `c68e39f60462f28d9be5e683d9cbe2c57b1a5027` 中的沙箱启动解析器
和持久会话摘要。
